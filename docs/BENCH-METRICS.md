# Метрики контрольного бенча (методика R3) — разбор

Справочник по метрикам `bench/p7-compare.sh`: что именно измеряется, как,
и как читать цифры. Свежие результаты —
[BENCH-V0.2.0-2026-10-13.md](BENCH-V0.2.0-2026-10-13.md); октябрьский
срез — [BENCH-P7-2026-10-06.md](BENCH-P7-2026-10-06.md).

## Общие принципы методики

| № | Приём | Зачем |
|---|-------|-------|
| 1 | **Медиана, не среднее** | Распределения таймингов длиннохвостые: один выброс уводит среднее, медиану — нет. В отчётах median + min + p95 + max |
| 2 | **Прогрев** (первый раунд отбрасывается) | Первый проход несёт холодные кэши: первый хендшейк, прогрев кода, создание файлов |
| 3 | **Ротация реализаций A→B→C** | Раунды идут по кругу (c→go→os→c→…), а не блоками — фоновая нагрузка бокса ложится на все реализации одинаково |
| 4 | **sha256-гейт** | Передача засчитывается только при совпадении sha256 с исходником; проверка стоит **вне** замеряемого окна. Битая передача = отбракованный раунд, а не красивая цифра |
| 5 | **Один стенд на всех** | Один ключ ed25519 (в двух форматах), один loopback, payload'ы на tmpfs — сравниваются реализации, а не окружения |

## 1. Throughput (пропускная способность)

**Операция.** Перенос файла целиком: `push` = клиент → сервер, `pull` = сервер → клиент. Механизмы честно различаются и это часть результата: OpenSSH — `scp` (копия поверх exec-канала), Go-форк — sftp-подсистема, ssh3-c — sftp-канал своего клиента.

**Замер.** `date +%s%N` (наносекундные настенные часы) вокруг всей передачи; МБ/с = фактический размер / секунды. Wall-clock «пользовательского опыта», не внутренний счётчик байт.

| № | Размер | Что показывает |
|---|--------|----------------|
| 1 | 512 МиБ | Установившийся режим: окна раскрыты, цена сессии амортизирована — чистая скорость **канала данных** |
| 2 | 8 МиБ | Setup-доминированный режим: фиксированная цена сессии (handshake + открытие каналов + вердикт) размазана на маленький файл — измеряет цену **коннекта**, не канала |

**Чтение.** QUIC-семейство (C, Go) гоняет TLS+QUIC **в user space**, OpenSSH — TCP+AES-NI в ядре: структурная разница классов, не дефект. Константные МБ/с на 8 МиБ — цена сессии, делённая на 8 МиБ.

## 2. Handshake (cold connect+auth+exec)

**Операция.** Полный холодный цикл: запуск процесса клиента → QUIC-хендшейк (TLS 1.3 поверх QUIC, 1-RTT) → аутентификация (JWT с подписью Ed25519) → HTTP/3 Extended CONNECT → открытие session-канала → exec no-op → exit-код.

**Замер.** Настенные часы вокруг **всего вызова клиента, включая запуск процесса** — поэтому min показывает почти чистую цену протокола.

**Чтение.** Структурный выигрыш QUIC-семейства: 1-RTT хендшейк + один раунд авторизации против TCP-хендшейка + многораундовой SSH2-аутентификации. Стабильность OpenSSH (узкий разброс) — kernel TCP без user-space планирования.

## 3. Mux warm exec (мультиплексированные сессии)

**Операция.** Латентность команды **поверх установленного мастер-соединения** (ControlMaster): слейв → локальный сокет/пайп → токен → аттач каналов → exec → вердикт. Хендшейк и авторизация не повторяются.

**Замер.** 3 блока × 100 exec'ов на реализацию (каждый блок — свежий мастер), медиана по 300.

**Чтение.** Профиль автоматизации/MCP: сотни команд в одной сессии. Здесь QUIC-хендшейк уже оплачен — соревнуется механика «пробросить команду». Валидные 300/300 — заодно доказательство стабильности мастера (лимиты сессий, отказы).

## 4. CPU / RAM сервера

**CPU.** Сэмплер каждые 50 мс читает `/proc/<pid>/stat`: дельта jiffies (USER_HZ=100) / реальное время → % **одного ядра** (>100% — дерево из нескольких процессов; для sshd замер по всему дереву). Замер — одна выделенная верифицированная передача со свежим демоном.

**RAM.** Пик VmRSS по тем же сэмплам.

**Чтение.** CPU показывает цену крипто+копий на насыщенном канале; RSS — стратегию буферизации (окна против «всего файла сразу»). Высокий RSS при нормальном CPU — узкое место в памяти, не в процессоре.

## 5. Manyfiles (каталог мелких файлов)

**Операция.** Рекурсивный перенос каталога из N файлов по 4 КиБ (`scp -r` / форк `-f -r` / харнес `-J -r`): `push` = загрузка дерева, `pull` = скачивание (дерево на удалённой стороне засеивается **вне** замеряемого окна тем же механизмом).

**Замер.** Wall-clock вокруг всей передачи; итог — files/s и агрегатные МБ/с; верификация — число файлов и суммарный размер на приёмнике.

**Чтение.** Метрика per-file/per-request оверхеда протокола и клиентского драйвера: N маленьких передач вместо одного потока. Размер N калибруется опытным путём так, чтобы разброс между реализациями превышал погрешность измерения (см. значения N в отчётах).

## Сводка: какая метрика на какой вопрос отвечает

| № | Метрика | Вопрос пользователя |
|---|---------|--------------------|
| 1 | Throughput 512 МиБ | «Как быстро качать файлы?» |
| 2 | Throughput 8 МиБ | «Быстро дернуть мелочь?» (цена сессии) |
| 3 | Handshake | «Как быстро зайти на хост?» |
| 4 | Mux warm exec | «Как быстро гонять сотни команд в сессии?» |
| 5 | Manyfiles | «Как быстро скопировать дерево мелких файлов?» |
| 6 | CPU/RAM | «Сколько сервер стоит на машине?» |

## Ограничения

- Только loopback; WAN/потери — netem-нога набора форка (`project/ssh3/bench/`, TESTPLAN R3).
- Механизмы не идентичны (scp против sftp-подсистемы против sftp-канала) — различие зафиксировано как часть результата.
- Бенч-бокс не выделенный: ambient-нагрузка выравнивается ротацией, хвосты (p95/max) публикуются.
