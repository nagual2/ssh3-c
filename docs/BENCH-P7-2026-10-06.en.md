# P7 control benchmark: ssh3-c vs Go fork vs OpenSSH (R3 methodology)
> Languages: [RU](BENCH-P7-2026-10-06.md) · EN (this file) · [DE](BENCH-P7-2026-10-06.de.md)

Date: 2026-10-06. Branch: `fix/p7-bench`. Run: `bench/p7-compare.sh` (repo); raw CSVs and logs — `/tmp/p7bench/{results,logs}/` (kept out of the repo).

## Environment

| # | Parameter | Value |
|---|-----------|-------|
| 1 | Testbed | WSL2, kernel 6.18.40.1, loopback 127.0.0.1, payload/output on tmpfs `/dev/shm` |
| 2 | Hardware | AMD Ryzen 5 4600H (AES-NI), 12 threads, RAM 7.6 GiB |
| 3 | OS | Ubuntu 24.04.4, bash, sudo only for the dedicated sshd |
| 4 | OpenSSH | 9.6p1 Ubuntu (`aes128-gcm@openssh.com`, BatchMode), dedicated sshd :2222 (own host key + `AuthorizedKeysFile`, system `~/.ssh` untouched) |
| 5 | Go fork | `francoismichel/ssh3` 0.1.26 (nagual2), `CGO_ENABLED=0 go build -tags disable_password_auth`, server :8023/udp, client `-f`/ControlMaster |
| 6 | ssh3-c | `ssh3-server version 0.1.0`, clang-18 `linux-release`, daemon :8022/udp (JWT pubkey `-K`), client `s3interop_client` (exec, `-J` sftp, `-3 -C -M`) |
| 7 | Authentication | one ed25519 keypair everywhere: PKCS8 PEM (JWT clients C and Go), OpenSSH format (ssh/scp); authorized keys as separate files, `~/.ssh3/authorized_identities` was created for the duration of the run and then removed |
| 8 | Tuning | defaults of all servers/clients (datagram sizing, windows) — nothing was tweaked |

Measurement: `date +%s%N` around the transfer; every transfer verified with sha256 (verification outside the measured window); the first round is a warmup and does not enter the tables; round order A→B→C (c→go→os) cyclically — ambient load falls on all equally; the final numbers are medians. CPU/RAM: `/proc/<pid>/stat` (USER_HZ deltas, CLK_TCK=100) + VmRSS peak, samples every 50 ms; for OpenSSH — aggregated over the process tree of the dedicated sshd. The caveat from BENCH-2026-09-29 stays in force: userspace QUIC (ours and Go) against kernel-adjacent OpenSSH is a structural difference, not a defect. Parallel agents (builds, valgrind) were running on the box — the background was the same for all implementations thanks to rotation.

## 1. Throughput bulk-transfer (MB/s, median of 7 rounds, sha-verified)

| # | Implementation (mechanism) | 512 MiB push | 512 MiB pull | 8 MiB push | 8 MiB pull |
|---|----------------------------|-------------:|-------------:|-----------:|-----------:|
| 1 | OpenSSH (scp, file copy) | **317.6** | **356.6** | 62.5 | 86.7 |
| 2 | Go fork (sftp subsystem, `-f`) | 17.6 | 23.8 | 21.9 | 38.5 |
| 3 | ssh3-c (`-J`, sftp channel) | 0/7 valid | 0/7 valid | 0/7 valid | 0/7 valid |

Reading the results:

1. The mechanisms are not identical, and that is part of the result: scp is a file copy over an exec channel; Go `-f` and C `-J` are the sftp subsystem/channel. The fork's canonical numbers (130–365 MB/s, `BENCH-2026-09-29`) were taken with an exec pipe (`cat` through a session) — the fork's sftp subsystem is 6–15× slower than its own pipe path.
2. ssh3-c: **0 of 28** transfers survive sha256. Causes — two defects of the sftp path (see "Findings"): intermittent data corruption (put appends +64 KiB, get duplicates the stream up to 2.2× the volume) and a put verdict that never completes. Earlier, on small files, the paths were at times byte-for-byte (cmp checks of 1–6 MiB pass); the failure is nondeterministic and worsens with volume/load.
3. The transport ceiling of ssh3-c is not sftp: the P2 echo on the same machine gives ~237 MB/s (median, `docs/PLAN.md` P2) — the level of the OpenSSH scp mechanism; the bottleneck is the application-level sftp path, not QUIC.

## 2. Handshake / cold session establish (exec no-op, median of 30 runs)

| # | Implementation | median | min | p95 | max |
|---|----------------|-------:|----:|----:|----:|
| 1 | ssh3-c | **62.9 ms** | 60.4 | 72.5 | 85.6 |
| 2 | Go fork (exec `true`) | 202.8 ms | 150.8 | 461.2 | 487.6 |
| 3 | OpenSSH (exec `true`) | 232.1 ms | 217.7 | 262.6 | 293.0 |

ssh3-c is 3.2–3.7× faster: QUIC 1-RTT + one authorization round (Bearer JWT) vs TCP+SSH2 authentication. The fork's p95 (461 ms) is background noise and client startup (plugin registration on every launch); the fork's own measurement on a quiet machine is 26 ms cold (`bench/exec-latency.sh`, 2026-10-04) — the "c < go < os" ordering holds in that case as well. Aside: for C the command is `printf s3-exec-ok` (the client's verification marker), for Go/OpenSSH it is `true`; both are no-ops.

## 3. Multiplexed sessions (ControlMaster, warm exec `true`)

| # | Implementation | median | min | p95 | max | valid |
|---|----------------|-------:|----:|----:|----:|-------|
| 1 | OpenSSH (ControlMaster/ControlPersist) | **14.1 ms** | 11.6 | 19.2 | 61.9 | 300/300 |
| 2 | Go fork (-control-master) | **9.4 ms** | 7.4 | 17.6 | 42.2 | 300/300 |
| 3 | ssh3-c (-3 -C -M) | 55.8 ms | 54.4 | — | 81.2 | 45/300 |

Reading the results:

1. Command latency is the owner's priority, and here ssh3-c has two structural problems. (a) A hard limit: after **15 sessions per master connection** the slaves fail fast (pattern 15/100 in each of the three blocks, 3×85 failures) — it looks like exhaustion of initial_max_streams_bidi without replenishing MAX_STREAMS on the master↔daemon path. (b) Warm exec ~56 ms — 4–6× slower than Go (9.4) and OpenSSH (14.1): the price of the master path's UDS bridge.
2. For Go and OpenSSH, multiplexing is fully functional: 1 handshake per block, 300/300 execs. The medians of both are noticeably below the cold handshake (§2) — the multiplexing effect is confirmed.
3. Aside: the C master cannot authenticate (`-U` is occupied by the socket path, `-K` is incompatible with the master), so for this stage the daemon ran in open mode (any non-empty Authorization, `app/ssh3_server.c`) — the auth cost is not included in the C figure (one-time per connection, does not affect warm exec).

## 4. CPU/RAM on the server under transfer (50 ms samples)

| # | Implementation | Load | CPU (tree) | RSS peak |
|---|----------------|------|-----------:|---------:|
| 1 | OpenSSH (sshd) | scp 512 MiB push | 102.0% | 27 MB |
| 2 | Go fork | sftp 512 MiB push | 84.9% (of a core) | 26 MB |
| 3 | ssh3-c | sftp 4 MiB put (clean) | 0.7% | 9 MB |

Reading the results:

1. ssh3-c at the current sftp quality spends almost no CPU (0.7%) — the 50 ms timer pump keeps the connection idle: the cost is moved from CPU to latency. This is not a merit but a symptom of finding #2.
2. The Go fork burns ~85% of a core on userspace crypto+QUIC at full speed — matches the "SSH3 price" from BENCH-2026-09-29 (there 16.1% mean on the weakest mechanism profile; here the channel is saturated).
3. OpenSSH ~102% across two processes of the tree (master+session) at 317–357 MB/s — kernel AES-NI is cheap both on CPU and in memory.

## Findings (blockers/debt of the ssh3-c application path)

1. **The SFTP channel corrupts data (both sides, intermittently)**: put appends +64 KiB (nondeterministically, more often under load/at volume), get duplicates the stream (8 MiB → 17.9 MiB in the measurement). Suspect: re-emission of the parked frame tail when the window is reopened (50 ms pump, "the window reopens on the next timer tick"). Until fixed, bulk sftp is unusable — sha verification rejects everything. A blocker for the packaging promise "sftp works".
2. **The put verdict never completes**: the client waits for a channel confirmation that never arrives; the attempt burns out on the deadline (the data is meanwhile on the server). Scenario 23 of the matrix runs small files — it does not catch this.
3. **ControlMaster: 15 sessions per connection** — slaves fail fast from the 16th onward; and ~56 ms per warm exec (4–6× worse than Go/OpenSSH). For the MCP profile (owner priority: command latency) this is the main functional gap versus the Go fork.
4. **Handshake — a strong side**: 62.9 ms, stable (max 85.6) — 3+× faster than both predecessors; the basis for claims in the R1 article.
5. **The CPU profile** will be honest once the pump is fixed (expected between Go and OpenSSH); the current 0.7% is an idling artifact, not efficiency.

## Deviations from the R3 methodology / brief

| # | Deviation | Reason |
|---|-----------|--------|
| 1 | ssh3-c not measured at 512 MiB; the table's 8 MiB — 0 valid rounds | the timer pump at ~0.2 MB/s makes 512 MiB a multi-hour affair; plus intermittent corruption — the sha gate rejects them |
| 2 | the ssh3-c CPU row taken manually at 4 MiB (the only clean size out of the 1/2/4/6/7/8 MiB bisection) | the scripted sha gate discards samples of broken transfers |
| 3 | the C master mux — against the daemon in open mode | the master cannot authenticate (see §3) |
| 4 | C cold exec — `printf s3-exec-ok` instead of `true` | the client's verdict requires the marker; both commands are no-ops |
| 5 | the throughput mechanisms differ (scp / sftp subsystem / sftp channel) | prescribed by the brief; the difference is documented as part of the result |
| 6 | the go handshake is noticeably worse than the fork's own measurement (26 ms) | background of parallel agents + client startup; the A→B→C rotation levels the comparison |

## Reproduction

```bash
# в WSL, сборки: worktree build/linux-release и /tmp/p7bench/bin
bash bench/p7-compare.sh --stage all          # ~25–30 мин, стенд в /tmp/p7bench
bash bench/p7-compare.sh --stage handshake    # отдельная стадия
```

The script brings up the testbed itself (C daemon `-K`, Go server, dedicated sshd :2222), tears it down when finished, and cleans up the home artifacts; binaries are launched under neutral names (`p7c-*`, `p7go-*`) — pkill sweeps of parallel agents by the names `ssh3-server`/`s3interop_*` do not kill the testbed.
