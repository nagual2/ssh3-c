# P7 контрольный бенч: ssh3-c vs Go-форк vs OpenSSH (методика R3)

Дата: 2026-10-06. Ветка: `fix/p7-bench`. Прогон: `bench/p7-compare.sh` (репо),
сырые CSV и логи — `/tmp/p7bench/{results,logs}/` (в репо не заходят).

## Окружение

| № | Параметр | Значение |
|---|----------|----------|
| 1 | Стенд | WSL2, kernel 6.18.40.1, loopback 127.0.0.1, payload/вывод на tmpfs `/dev/shm` |
| 2 | Железо | AMD Ryzen 5 4600H (AES-NI), 12 потоков, RAM 7.6 GiB |
| 3 | ОС | Ubuntu 24.04.4, bash, sudo только для выделенного sshd |
| 4 | OpenSSH | 9.6p1 Ubuntu (`aes128-gcm@openssh.com`, BatchMode), выделенный sshd :2222 (свой host key + `AuthorizedKeysFile`, системный `~/.ssh` не тронут) |
| 5 | Go-форк | `francoismichel/ssh3` 0.1.26 (nagual2), `CGO_ENABLED=0 go build -tags disable_password_auth`, сервер :8023/udp, клиент `-f`/ControlMaster |
| 6 | ssh3-c | `ssh3-server version 0.1.0`, clang-18 `linux-release`, демон :8022/udp (JWT pubkey `-K`), клиент `s3interop_client` (exec, `-J` sftp, `-3 -C -M`) |
| 7 | Аутентификация | одна пара ed25519 везде: PKCS8 PEM (JWT-клиенты C и Go), OpenSSH-формат (ssh/scp); авторизованные ключи — отдельные файлы, `~/.ssh3/authorized_identities` создавался на время прогона и убран |
| 8 | Тюнинг | дефолты всех серверов/клиентов (datagram sizing, окна) — ничего не крутили |

Замер: `date +%s%N` вокруг передачи; каждый трансфер верифицирован sha256
(верификация вне замеряемого окна); первый раунд — прогрев, в таблицы не идёт;
порядок раундов A→B→C (c→go→os) по кругу — ambient-нагрузка ложится на всех
одинаково; итог — медианы. CPU/RAM: `/proc/<pid>/stat` (USER_HZ-дельты,
CLK_TCK=100) + пик VmRSS, сэмплы каждые 50 мс; для OpenSSH — суммарно по
дереву процессов выделенного sshd. Оговорка из BENCH-2026-09-29 действует:
userspace-QUIC (наш и Go) против kernel-adjacent OpenSSH — структурная разница,
не дефект. На боксе параллельно работали агенты (сборки, valgrind) — фон
одинаковый для всех реализаций благодаря ротации.

## 1. Throughput bulk-transfer (MB/s, медиана 7 раундов, sha-verified)

| № | Реализация (механизм) | 512 MiB push | 512 MiB pull | 8 MiB push | 8 MiB pull |
|---|----------------------|-------------:|-------------:|-----------:|-----------:|
| 1 | OpenSSH (scp, файл-копия) | **317.6** | **356.6** | 62.5 | 86.7 |
| 2 | Go-форк (sftp-подсистема, `-f`) | 17.6 | 23.8 | 21.9 | 38.5 |
| 3 | ssh3-c (`-J`, sftp-канал) | 0/7 валидных | 0/7 валидных | 0/7 валидных | 0/7 валидных |

Чтение результатов:

1. Механизмы не идентичны и это часть результата: scp — файл-копия по exec-каналу,
   Go `-f` и C `-J` — sftp-подсистема/канал. Канонические цифры форка
   (130–365 MB/s, `BENCH-2026-09-29`) сняты exec-пайпом (`cat` через сессию) —
   sftp-подсистема форка в 6–15 раз медленнее собственного пайп-пути.
2. ssh3-c: **0 из 28** передач не отбракованы sha256. Причины — два дефекта sftp
   пути (см. «Находки»): интермиттентная порча данных (put пишет +64 KiB, get
   дублирует поток до 2.2× объёма) и незавершаемый вердикт put. Раньше на малых
   файлах пути бывали байт-в-байт (cmp-проверки 1–6 MiB проходят), отказ
   недетерминированный и усиливается с объёмом/нагрузкой.
3. Потолок транспорта ssh3-c — не sftp: эхо P2 на этой же машине даёт ~237 MB/s
   (медиана, `docs/PLAN.md` P2) — уровень scp-механизма OpenSSH; узкое место —
   прикладной sftp-путь, а не QUIC.

## 2. Handshake / cold session establish (exec no-op, медиана 30 прогонов)

| № | Реализация | median | min | p95 | max |
|---|------------|-------:|----:|----:|----:|
| 1 | ssh3-c | **62.9 ms** | 60.4 | 72.5 | 85.6 |
| 2 | Go-форк (exec `true`) | 202.8 ms | 150.8 | 461.2 | 487.6 |
| 3 | OpenSSH (exec `true`) | 232.1 ms | 217.7 | 262.6 | 293.0 |

ssh3-c в 3.2–3.7 раза быстрее: QUIC 1-RTT + один раунд авторизации (Bearer JWT)
против TCP+SSH2-аутентификации. p95 форка (461 ms) — шум фона и старт клиента
(регистрация плагинов каждый запуск); собственный замер форка на тихой машине —
26 ms cold (`bench/exec-latency.sh`, 2026-10-04) — порядок «c < go < os» при
этом сохраняется. Отступление: у C команда `printf s3-exec-ok` (верификационный
маркер клиента), у Go/OpenSSH — `true`; обе — no-op.

## 3. Мультиплексированные сессии (ControlMaster, warm exec `true`)

| № | Реализация | median | min | p95 | max | валидные |
|---|------------|-------:|----:|----:|----:|----------|
| 1 | OpenSSH (ControlMaster/ControlPersist) | **14.1 ms** | 11.6 | 19.2 | 61.9 | 300/300 |
| 2 | Go-форк (-control-master) | **9.4 ms** | 7.4 | 17.6 | 42.2 | 300/300 |
| 3 | ssh3-c (-3 -C -M) | 55.8 ms | 54.4 | — | 81.2 | 45/300 |

Чтение результатов:

1. Command latency — приоритет владельца, и здесь у ssh3-c две структурные
   проблемы. (а) Жёсткий лимит: после **15 сессий на мастер-коннект** слейвы
   падают фейстейлом (паттерн 15/100 в каждом из трёх блоков, 3×85 отказов) —
   похоже на исчерпание initial_max_streams_bidi без пополнения MAX_STREAMS на
   пути мастер↔демон. (б) Тёплый exec ~56 ms — в 4–6 раз медленнее Go (9.4) и
   OpenSSH (14.1): цена UDS-моста мастер-пути.
2. У Go и OpenSSH мультиплексирование полностью функционально: 1 handshake на
   блок, 300/300 exec'ов. Медианы обоих — заметно ниже холодного handshake
   (§2), эффект мультиплексирования подтверждён.
3. Отступление: C-мастер не умеет аутентифицироваться (`-U` занят путём сокета,
   `-K` с мастером несовместим), демон для этой стадии работал в open-режиме
   (любой непустой Authorization, `app/ssh3_server.c`) — auth-цена в цифру C не
   входит (разовая на коннект, на warm-exec не влияет).

## 4. CPU/RAM на сервере под передачей (сэмплы 50 ms)

| № | Реализация | Нагрузка | CPU (дерево) | RSS пик |
|---|------------|----------|-------------:|--------:|
| 1 | OpenSSH (sshd) | scp 512 MiB push | 102.0% | 27 MB |
| 2 | Go-форк | sftp 512 MiB push | 84.9% (ядра) | 26 MB |
| 3 | ssh3-c | sftp 4 MiB put (чистый) | 0.7% | 9 MB |

Чтение результатов:

1. ssh3-c при current-качестве sftp почти не тратит CPU (0.7%) — 50-мс
   таймерный насос держит соединение простаивающим: цена перенесена из CPU в
   латентность. Это не заслуга, а симптом находки №2.
2. Go форк жжёт ~85% ядра на userspace-крипто+QUIC на полной скорости —
   соответствует «цене SSH3» из BENCH-2026-09-29 (там 16.1% mean на слабейшем
   профиле механизма; здесь канал насыщен).
3. OpenSSH ~102% на два процесса дерева (master+session) при 317–357 MB/s —
   kernel AES-NI дёшев и на CPU, и по памяти.

## Находки (блокеры/долги прикладного пути ssh3-c)

1. **SFTP-канал портит данные (обе стороны, интермиттентно)**: put дописывает
   +64 KiB (недетерминированно, чаще под нагрузкой/на объёме), get дублирует
   поток (8 MiB → 17.9 MiB в замере). Suspect: повторный emit припаркованного
   хвоста кадра при переоткрытии окна (50-мс насос, «the window reopens on the
   next timer tick»). До починки bulk-sftp неприменим — sha-верификация
   отбраковывает всё. Блокер для packaging-обещания «sftp работает».
2. **Вердикт put не завершается никогда**: клиент ждёт подтверждения канала,
   которое не приходит; попытка сгорает по дедлайну (данные при этом на
   сервере). Сценарий 23 матрицы гоняет малые файлы — не ловит.
3. **ControlMaster: 15 сессий на коннект** — фейстейл слейвов с 16-й; и ~56 ms
   на тёплый exec (4–6× хуже Go/OpenSSH). Для MCP-профиля (owner priority:
   command latency) это главный функциональный разрыв с Go-форком.
4. **Handshake — сильная сторона**: 62.9 ms, стабильно (max 85.6) — быстрее
   обоих предшественников в 3+ раза; база для claims в статью R1.
5. **CPU-профиль** при починке насоса станет честным (ожидаемо между Go и
   OpenSSH); текущие 0.7% — артефакт простаивания, не эффективность.

## Отклонения от методики R3 / брифа

| № | Отклонение | Причина |
|---|------------|---------|
| 1 | ssh3-c не измерен на 512 MiB; в таблице 8 MiB — 0 валидных раундов | таймерный насос ~0.2 MB/s делает 512 MiB многочасовыми; плюс интермиттентная порча — sha-гейт отбраковывает |
| 2 | CPU-строка ssh3-c снята вручную на 4 MiB (единственный чистый размер из бисекции 1/2/4/6/7/8 MiB) | скриптовый sha-гейт отбрасывает сэмплы битых передач |
| 3 | C-мастер mux — против демона в open-режиме | мастер не может аутентифицироваться (см. §3) |
| 4 | C cold exec — `printf s3-exec-ok` вместо `true` | вердикт клиента требует маркер; обе команды — no-op |
| 5 | механизмы throughput различаются (scp / sftp-подсистема / sftp-канал) | предписано брифом; различие задокументировано как часть результата |
| 6 | go handshake заметно хуже собственного замера форка (26 ms) | фон параллельных агентов + старт клиента; ротация A→B→C выравнивает сравнение |

## Воспроизведение

```bash
# в WSL, сборки: worktree build/linux-release и /tmp/p7bench/bin
bash bench/p7-compare.sh --stage all          # ~25–30 мин, стенд в /tmp/p7bench
bash bench/p7-compare.sh --stage handshake    # отдельная стадия
```

Скрипт сам поднимает стенд (демон C `-K`, сервер Go, выделенный sshd :2222),
гасит его по завершении, артефакты дома убирает; бинарники запускает под
нейтральными именами (`p7c-*`, `p7go-*`) — pkill-развёртки параллельных агентов
по именам `ssh3-server`/`s3interop_*` стенд не убивают.
